# Administrator credential rotation — incident runbook

**Status: action required by the platform owner.**

A fallback administrator username, email address, and password were hardcoded
in `core/management/commands/bootstrap_superuser.py`, and that command ran
automatically on every production deploy. A second command,
`create_demo_user`, also carried a hardcoded default password for a superuser
account and printed it to the deploy log.

The code has been fixed (see *What the code fix changed*, below). **The code
fix does not rotate anything that already exists in production.** Until the
steps in this document are completed, treat every administrator account on the
live service as compromised.

This document contains no credential values, and none should ever be added to
it. Do not paste passwords, tokens, or screenshots into this file, into commit
messages, or into issue trackers.

---

## 1. Assume compromise

The credentials were committed to a public-history repository and were
reachable from `main`. Assume they are known to third parties, regardless of
whether any misuse has been observed. Deleting them from the latest commit is
**not** sufficient — they remain in git history (see §8).

## 2. Rotate the administrator passwords — do this first

1. Sign in to the production environment through an authorised secure channel
   (the Render dashboard for the `ecoiq` service, or your own admin session —
   not a shared or unmanaged device).
2. Change the password of **every** affected administrator account. Do this in
   the Django admin (`/admin/`) or via a one-off shell:

   ```bash
   python manage.py changepassword <username>
   ```

   `changepassword` prompts interactively and does not echo the value.
3. Use a unique, high-entropy password generated by a password manager. Do not
   reuse a password from any other system.
4. If the compromised password was reused anywhere else — email, Render,
   GitHub, the database, any third-party service — rotate it there too.

## 3. Review every privileged account

```bash
python manage.py shell -c "
from django.contrib.auth import get_user_model
U = get_user_model()
for u in U.objects.filter(is_staff=True).order_by('username'):
    print(u.username, u.email, 'super' if u.is_superuser else 'staff',
          u.is_active, u.last_login, u.date_joined)
"
```

- Confirm every account listed is one you recognise and still need.
- Deactivate (`is_active = False`) anything unknown, stale, or unnecessary.
  Prefer deactivating over deleting while the incident is open — a deactivated
  account preserves the audit trail.
- Pay particular attention to accounts created around or after the date the
  bootstrap command was introduced.

## 4. Review access logs

- Render → the `ecoiq` service → **Logs**: look for `/admin/login/` activity,
  especially successful logins from unfamiliar IP addresses or at unusual
  hours.
- Check `django-admin-log` (`/admin/admin/logentry/`) for object changes you
  did not make.
- Note that Render retains logs for a limited window; capture anything
  relevant now rather than later.

## 5. Invalidate active sessions

If compromise is suspected rather than merely possible, terminate all existing
sessions. With the default database session backend:

```bash
python manage.py shell -c "
from django.contrib.sessions.models import Session
print(Session.objects.all().delete())
"
```

This signs out every user, including you. Changing a user's password already
invalidates that user's sessions when `SessionAuthenticationMiddleware`
semantics apply, but a full flush is the safe option after a credential leak.

## 6. `SECRET_KEY` — consider carefully

`DJANGO_SECRET_KEY` is generated by Render (`generateValue: true`) and was not
part of this leak, so rotating it is **optional**. If you rotate it anyway:

- all sessions are invalidated;
- all password-reset links, signed cookies, and any other signed or
  `signing`-serialised data become invalid;
- anything persisted that was signed with the old key cannot be verified.

Rotate it only if you have reason to believe the key itself was exposed.

## 7. Review the surrounding access surface

- **GitHub** (`Alizhan39/ecoiq-v1`): collaborators, deploy keys, personal
  access tokens, and installed OAuth apps.
- **Render**: team members, API keys, and the environment-variable list for the
  `ecoiq` service — confirm no `BOOTSTRAP_ADMIN_*` variable is left set.
- **Database**: the `ecoiq-db` credentials, and anything that holds a copy of
  them.
- **Deploy logs**: earlier deploys printed the bootstrap outcome; older logs may
  also contain a demo password printed by `create_demo_user`.

## 8. Git history

The credentials remain in git history. Removing a secret from the current tree
does not remove it from earlier commits, from forks, or from anything already
cloned or cached by GitHub. **Rotation (§2) is mandatory and is what actually
ends the exposure** — history cleanup only reduces future discoverability.

See the *Git history status* section of the remediation report for the proposed
`git filter-repo` procedure. Do not rewrite shared history without a
coordinated plan: it changes every downstream commit hash and requires every
collaborator to re-clone.

## Creating an administrator the safe way

`bootstrap_superuser` no longer runs on deploy and no longer has any default
credentials. It is now a manual, one-time operation for an authorised operator.

1. Open a one-off shell against the production service (Render → the `ecoiq`
   service → **Shell**).
2. Set the three variables **for that single command only**, so they are not
   persisted into the service's environment:

   ```bash
   BOOTSTRAP_ADMIN_USERNAME=<username> \
   BOOTSTRAP_ADMIN_EMAIL=<email> \
   BOOTSTRAP_ADMIN_PASSWORD=<generated-password> \
     python manage.py bootstrap_superuser
   ```

3. Sign in immediately and confirm the account works.
4. **Remove `BOOTSTRAP_ADMIN_PASSWORD` from the environment right away** if it
   was set anywhere persistent (Render dashboard → Environment). Never store it
   as a service environment variable, and never commit it.
5. Clear the shell history for that session if the value was typed inline.

Behaviour worth knowing:

- If any of the three variables is missing, empty, or whitespace-only, the
  command raises `CommandError` and creates nothing. It names the missing
  variables; it never prints a value.
- If a user with that username already exists, the command reports so and exits
  **without changing the existing password**. Use `changepassword` to rotate an
  existing account.
- The password is hashed by Django's user manager and never written to stdout.

## What the code fix changed

| File | Change |
| --- | --- |
| `core/management/commands/bootstrap_superuser.py` | Removed the hardcoded username, email, and password defaults. All three now come from the environment; missing or blank values raise `CommandError`. Existing accounts are never overwritten. The password is never printed. |
| `predeploy.sh` | Removed the automatic `bootstrap_superuser` call. Replaced with a comment documenting the manual procedure. |
| `core/management/commands/create_demo_user.py` | Removed the hardcoded default password; it must now be supplied via `--password` or `DEMO_USER_PASSWORD`. The password is no longer printed on success. |
| `core/tests_bootstrap_superuser.py` | Regression tests: missing/blank configuration is rejected, credentials are never printed, no default credentials reappear, deploy scripts do not invoke the command. |
| `.github/workflows/secret-scan.yml` | Gitleaks runs on pull requests and pushes to `main` and fails the build on a probable secret. |

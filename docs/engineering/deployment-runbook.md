# Deployment runbook

How EcoIQ deploys on Render, what each phase is allowed to do, and the manual
operations that are deliberately *not* part of a deploy.

## Phases

| Phase | Script | Runs | Database access | Fails the deploy? |
| --- | --- | --- | --- | --- |
| Build | `build.sh` (after `pip install -r requirements.txt` in `render.yaml`) | Every deploy, build network | **None** — the internal Postgres hostname does not resolve here | Yes (`set -euo pipefail`) |
| Release | `predeploy.sh` (Render Pre-Deploy Command) | Once per deploy, runtime network | Migrations | **Yes** |
| Runtime | `start.sh` (Start Command) | Every process start | Serving only | n/a |

The separation is deliberate: build produces artefacts, release changes schema
exactly once, runtime only serves.

## What changed and why

Previously the release phase ran `set +e` and ended in `exit 0`, so a failed
migration produced a **green deploy on a half-migrated schema**, and `start.sh`
ran `migrate` again on every process start — meaning any restart, autoscale
event, or OOM kill could mutate the production schema, with workers racing.

Now:

- `predeploy.sh` uses `set -euo pipefail`, retries the *connection* up to five
  times, and **exits 1** if migrations do not succeed. Render aborts the deploy
  and the previous release keeps serving.
- `predeploy.sh` then runs `python manage.py check --deploy --fail-level ERROR`.
- `start.sh` does not migrate. It launches Gunicorn and nothing else.
- `build.sh` no longer re-runs `pip install` (`render.yaml`'s build command
  already does it).

### If a deploy now fails on migrations

That is the intended behaviour — it means the schema change did not apply. Do
not work around it by re-adding `|| true`. Read the migration error in the
Render deploy log, fix the migration, and redeploy. If the database was simply
unreachable, redeploying once it is back is sufficient.

## Manual operator actions

These used to run automatically on every deploy. They are idempotent, but they
write to production data, and a deploy is the wrong trigger for that: it made
every deploy slower, made deploy logs noisy, and meant a seeding bug could
overwrite live data without anyone asking for it.

Run them from a Render one-off shell against the `ecoiq` service, only when the
data actually needs to be (re)established — typically once, when standing up a
new environment.

```bash
python manage.py seed_countries
```

```bash
python manage.py seed_global_companies && python manage.py seed_phase2_companies
```

```bash
python manage.py add_400_companies
```

```bash
python manage.py seed_score_history
```

```bash
python manage.py focus_target_markets
```

```bash
python manage.py seed_legacy_safe
```

Each is idempotent (safe to re-run). Run them one at a time and read the output
— unlike the old deploy step, nothing here hides a failure.

## Required environment variables

The application now refuses to start in production (`DEBUG=False`) if any of
these is missing or unsafe, rather than falling back to an insecure default:

| Variable | Requirement |
| --- | --- |
| `DJANGO_SECRET_KEY` | Required. No fallback. Generated by the Render blueprint. |
| `ALLOWED_HOSTS` | Required, explicit hostnames. `*` is rejected. |
| `DATABASE_URL` | Required. No SQLite fallback in production. |

Optional but worth setting:

| Variable | Default | Effect if unset |
| --- | --- | --- |
| `EMAIL_BACKEND` | console backend | Outbound email is written to the log and **never delivered**. A warning is printed at startup. |
| `LOG_LEVEL` | `INFO` in production | Root log level. |
| `ECOIQ_SEMANTIC_SEARCH_ENABLED` | `false` | Keeps `/api/v1/semantic-search/` on keyword search. Do not enable until `sentence-transformers` is installed *and* `league.Company` has an `embedding` column. |

A `.env` file no longer overrides real environment variables
(`load_dotenv(override=False)`), so a stray `.env` on a host cannot silently
replace production configuration.

## Gunicorn

`start.sh` runs 1 worker × 4 gthread threads with `--max-requests 300`. This is
sized for the Render Starter plan's 512 MB: WeasyPrint PDF generation is
memory-hungry and accumulates, which is what `--max-requests` recycling
addresses. **Do not raise `--workers` without raising the plan** — each worker
is a full Python process carrying pandas, scikit-learn, and WeasyPrint.
